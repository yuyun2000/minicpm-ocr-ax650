# 表格图片 OCR 乱序问题的根因与修复（2026-11-11）

## 现象

用户上传一张表格截图（1100×986，浅灰表格线），`page`（整页切片）模式输出：

```
Visual Token Compr ... ession Ratio 4x ... 16x 4x
General MMBen ... ch 83.17 ... 81.89 81.2
MMStar ... 69.53 ... 68.80 68.0
```

每个单元格/片段其实识别对了，但**阅读顺序被打乱、列被拆散**，人读不了。

## 根因（已复现验证）

`page` 模式按官方 MiniCPM-V 切片规则切图：1100×986 的图被切成 `grid=[2,3]`，即 **2 行 × 3 列共 6 片**：

- 一个完整表格被沿**垂直方向切成 3 条列带**，每片只含表格的一部分列；
- 每片用 `Text Recognition:`（纯文本）识别，输出自然按列带顺序排列；
- 服务端再按行优先拼接 → 列带交错，表格结构丢失。

同时确认：**整表一次性送（region + `Table Recognition:`）输出 OTSL 完全正确** —— 说明模型能力没问题，
是切分策略/提示词选错。

## 修复：表格模式 + 自动模式（服务端）

`board_app.py` 新增：

1. `looks_like_table()`：缩放到 448 后统计水平/垂直长线（阈值 235 覆盖浅灰表格线）；
   实测 表格截图 v_rules 15~90、正文页 v_rules ≈10，区分度足够。
2. `mode=table`：整表识别
   - `max(w,h) ≤ 2048`：**整张表一次** letterbox 到 448 + `Table Recognition:` → OTSL → Markdown；
   - 更大的表：**只按行切分**（保留全部列，6% 重叠），每片出 OTSL，再按行合并去重 → 一个 Markdown 表。
3. `mode=wide`：宽条文字（w ≥ 2.5h 且 w ≥ 1200）按列分块识别后顺序拼接（阅读顺序不丢）。
4. `mode=auto`（默认）：表格 → 表格模式；竖长且大（h≥1.2w 且长边≥1200，或长边≥2200）→ 整页模式；
   宽条 → wide；其余 → 单区域。

Web 前端默认选中「自动（推荐）」，也可手动选 表格 / 整页 / 单区域。

## 验证（板端实测）

| 输入 | 模式 | 结果 |
|---|---|---|
| 用户表格 1100×986 | `auto`（判为 table） | **21.9 s**，输出正确 Markdown 表（6 列 × 10 行：Visual Token Compression Ratio / General / STEM 全对） |
| 用户表格 1100×986 | `table` | 同上 |
| 用户表格 1100×986 | `page`（修复前路径） | 复现乱序：列带交错（6 片） |
| 宽条文字 1600×200 | `auto`（判为 wide） | 11.3 s，2 块按顺序拼接，内容可读 |

## 仍然存在的限制（需要版面模型才能根治）

- **整页文档里的表格**：整页切片仍可能把表格切开（无版面模型）。当前可用「先在网页上切出表格区域，用表格模式」。
- 真正的解法是版面检测（PP-DocLayoutV3 不适合 AX650；建议 **DocLayout-YOLO**，纯卷积、AX650 友好）：
  检测表格/文本/图片区域 → 表格区域走表格模式、文本区域走单区域 → 按阅读顺序组装。
